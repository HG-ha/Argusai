# 企业安全工作流

[文档首页](Home.md) · [Agent 与会话](Agent-and-Sessions.md) · [自动化](Automation.md) · [数据边界](Data-and-Safety.md)

ArgusAI 可以把资产信息、接口、流量、日志和样本组织成连续的安全工作：Agent 先梳理目标与材料，维护检查计划，再调用工具补充证据、跟踪问题，按需要安排后续巡检或复测。

本页给出内网安全防护、应用安全防护、攻击溯源和持续攻防的操作路线。它们是供团队试用和调整的工作方式，不代表客户部署记录。正式接入时，先确定负责人、授权边界、允许进入模型的材料和验收要求。

## 先给 Agent 一份明确的工作约定

| 项目 | 需要说明的内容 |
| --- | --- |
| 业务目标 | 要回答什么问题，例如新增暴露服务、发布风险、异常访问路径或检测是否有效 |
| 资产与身份 | 已授权的主机、网段、域名、应用、设备与测试账号；明确排除项 |
| 环境与动作 | 生产或测试环境、允许读取的资料、可使用的工具、是否允许主动请求与限速要求 |
| 材料处理 | 哪些日志、代码、账号标识或流量可以交给模型；哪些仅允许在本机保存或脱敏摘要 |
| 运行节奏 | 一次性分析、限时观察、任务续跑还是周期巡检；执行窗口、通知与停止条件 |
| 交付标准 | 证据位置、结论置信度、未覆盖内容、问题负责人和复测方式 |

把已确认的约定、基线和稳定检查步骤保存到 Case、知识库或 Skill，后续任务引用它们。授权已经清楚时，Agent 可以按约定主动推进；缺少必要信息时，应把问题记为阻塞项，不能自行扩大范围。

## 内网安全防护与主动巡检

### 准备材料

准备授权资产清单、系统负责人、已知端口与服务基线，以及已有的网络、主机或安全设备报告。资产清单应能区分测试与生产、关键业务与普通服务，并列出明确不允许探测的对象。

如果允许远程采集，准备已有的 SSH Host 配置或 SSH agent，并说明哪些主机可访问、允许读取哪些信息。密码、私钥和令牌不写入任务提示词或定时上下文。没有 SSH 权限时，可以分析已提供的主机资料，或只做获准的网络侧观察。

### Agent 如何组织工作

1. 读取资产清单与历史基线，建立“主机—服务—业务用途—证据缺口”的检查矩阵，并为需要补充的材料建立待办。
2. 在 scope 内使用主机发现、主机画像与暴露面分析工具，整理新增服务、开放端口和需要核实的风险线索。服务 banner 或版本匹配只是线索，应结合实际配置与业务用途判断。
3. 需要主机侧证据时，使用已经授权的 SSH 连接读取监听端口、防火墙摘要、失败登录统计或关键服务版本，并记录实际采集目标。`local_attack_surface_snapshot` 观察的是运行 ArgusAI 的本机；本机的 `ss`、`ufw` 等输出不能当成远程服务器的状态。
4. 对照上次基线，按业务影响安排复核顺序。将“新增暴露”“已核实配置风险”“材料不足”分开记录，为下一轮保留检查点。
5. 提交防护建议、负责人与验收条件。防火墙变更、服务重启、账号停用和生产加固应进入团队的变更流程，不能作为普通巡检的自动后续动作。

### 执行节奏

首次检查在当前会话完成即可；多步骤分析不需要默认创建定时任务。需要每日或每周巡检时，保存检查手册，再使用 `cron` 或 `interval`。独立巡检可以选择 `new_session`，跟踪一个关键系统则可以选择 `dedicated_session`。

每次对比应记录资产基线版本、检查时间与跳过项。有变化、执行失败或需要人工处理时通知；没有变化时按约定保持安静。频率应与授权窗口、资产规模和探测成本匹配。

### 证据与交付

交付可包含资产与服务变化表、风险复核队列、主机侧采集摘要和防护建议。每条结论关联目标、时间与时区、工具参数、输出片段和证据引用，并说明该轮未能检查的主机及原因。

可复制任务：

```text
请为我提供的授权资产清单建立内网安全检查计划。
先读取现有资产、服务基线和日志摘要，按业务用途确定检查顺序并维护待办。
只在清单范围内执行获准的轻量发现与暴露面复核；没有明确授权的主机不要探测。
有主机侧信息缺口时，只通过已配置、已授权的 SSH Host 读取约定信息；
没有远程权限则保留缺口，不要用本机命令替代远程采集。
对照基线记录新增暴露与待核实风险，给出证据、置信度和负责人的下一步。
本轮只做检查和建议，不修改防火墙、账号或服务，也不自动创建长期计划。
```

完成首次检查后，可以另行要求把已确认的手册配置为周期巡检，见[自动化](Automation.md)。

## 应用安全防护与业务审计

### 准备材料

准备预发布地址、发布变更说明、允许使用的测试身份，以及 HAR、JS、接口文档或已有扫描结果。说明业务流程、敏感操作和账号角色，限定测试域名、请求频率，以及是否允许写入测试数据。

生产应用可以先从授权采集的流量、日志和代码材料入手。浏览器登录态、Cookie 与请求正文可能包含业务数据，应先确定模型可接收的字段与脱敏方式。

### Agent 如何组织工作

1. 建立本次变更的 Case，整理接口、身份、关键参数与数据流。Agent 根据材料确定业务检查待办，不能把一份固定扫描清单当作全部覆盖范围。
2. 组合静态 JS、接口清单、浏览器和代理证据，检查认证、访问控制、输入处理、上传与相关业务路径。先核对异常请求的上下文，再决定哪些疑点值得验证。
3. 选择适用的内置检查或外部工具，记录实际执行范围。需要在线验证时，先给出方法、预期信号和影响，在批准的范围内执行最小探针。
4. 将已核实问题、疑似线索、缺少材料和本轮未覆盖内容分别归档，按风险与业务影响安排下一步。
5. 保存复现条件与材料，为研发排查和整改复测提供相同的基准。

应用防护还可以持续跟踪接口变化、新增被动发现、认证异常与发布后的配置差异。扫描器、浏览器和代理是 Agent 的工作手段；检查顺序、证据补全与问题跟踪由任务计划组织。

### 执行节奏

上线审计可在发布窗口完成；多轮调查使用现有或专属会话继续。测试构建完成后，可以通过签名 Webhook 触发新材料审查，也可以观察指定报告目录的文件变化。事件发送端和报告落盘流程需与现有系统对接。

主动请求、代理改写与阻断分别评估影响。普通防护巡检不应自行部署规则、修改业务数据或把已获准的测试扩展到生产。

### 证据与交付

交付应包含接口与身份覆盖、问题的业务条件、请求与响应或代码依据、验证状态、修复建议及未覆盖范围。浏览器或代理观察、扫描命中和人工确认的结论应能相互关联。

可复制任务：

```text
请审查这次预发布变更，目标只限我提供的测试域名和测试账号。
先读取变更说明、HAR、JS 与接口资料，不发主动请求。
主动整理接口、身份与数据流，根据业务流程建立检查待办；为每条疑点标明证据来源。
需要在线验证时，先给出方法、预期信号、请求数量与影响，交给我确认。
结果区分已核实、待验证、缺少材料和未覆盖内容，并保存可用于整改复测的条件。
不要修改生产配置、写入业务数据或自动部署防护规则。
```

具体界面操作见[Web 审计与代理](Web-Audit-and-Proxy.md)，样本与客户端分析见[逆向工作台](Reverse-Workbench.md)。

## 攻击溯源与事件辅助调查

### 准备材料

准备已经获准处理的应用、网关、WAF、EDR、主机或云审计日志，以及关联流量、样本和已有告警。无需一次提供全部日志：先限定事件窗口、关键系统与可用于关联的字段，再按证据缺口补充。

保留原始材料的来源、采集时间和引用。区分日志事件时间与材料采集时间，记录各来源时区、已知时钟偏移、保留范围及可能丢失的区间。需要远程补采时，使用明确授权的只读连接，并记录真正的远程目标。

### Agent 如何组织工作

1. 建立调查 Case，梳理已知事实与待回答问题，为不同材料安排待办或小队分工，例如应用访问、身份活动、主机进程与样本分析。
2. 将大文件保存为产物，读取与问题相关的片段。先归一化时间和实体，再关联请求 ID、trace ID、账号、来源地址、会话、进程及文件等标识。
3. 建立跨源时间线，标明每个事件来自哪份材料。对时间漂移、NAT、代理、共享地址、日志轮转和重复告警保留解释，不把表面相邻的事件直接串成因果链。
4. 从证据提出可能的入口、访问路径与影响假设，并列出替代解释和验证缺口。IP、域名、样本特征或单条 IOC 可以支持技术线索，不能独立证明真实攻击者身份。
5. 对相关样本使用静态分诊与已授权的工具分析，将产物关联到 ReverseJob 或 Case。样本动态执行与现场处置需要单独评估，不能默认在分析主机上运行不可信程序。
6. 随新证据更新结论与置信度，输出可供响应团队决策的调查材料。没有检索到相关记录时，同时说明实际覆盖的日志范围，不能将日志缺口写成“没有发生”。

### 执行节奏

一次性事件先在当前会话推进。需要持续补齐材料时，使用 `dedicated_session` 保留假设、待办和证据索引；也可用 `file_change` 分析新增导出日志。

检查点应记录已处理材料、时间窗口或读取位置、去重依据与下一步问题。遇到文件轮转、补发日志或时间范围变化时，先确认覆盖缺口，再继续分析。必要人工决定或缺失授权应阻塞并通知，不应靠扩大自动审批继续。

### 证据与交付

| 交付内容 | 应能回答的问题 |
| --- | --- |
| 带来源的事件时间线 | 发生了什么、何时发生、事件顺序依据是什么 |
| 技术路径与影响假设 | 哪些入口、身份、系统或数据可能相关，哪些仅是假设 |
| 置信度与替代解释 | 每项结论依赖什么证据，是否存在其他合理解释 |
| 覆盖与证据缺口 | 看过哪些来源和时间段，还缺什么、需要谁补充 |
| 响应建议与后续待办 | 需要哪些人工决策、补采或最小验证；哪些操作尚未执行 |

可复制任务：

```text
请围绕我指定的事件窗口，分析已提供的网关、应用、主机与身份日志。
先建立证据索引，记录来源、事件时区、采集时间、覆盖范围与已知时钟偏移。
按请求/trace ID、账号、会话、来源地址、进程和文件线索做跨源关联，主动列出调查假设与缺口。
每个时间线事件附材料引用；结论区分直接观察、推断和待验证，并说明置信度与替代解释。
不得仅凭 IP、域名或单条 IOC 推断真实攻击者身份。
只处理允许进入模型的字段；完整敏感日志保留在本地，不整段回传。
若需要补采远程资料，只提出已授权主机的只读采集计划，确认后再执行。
不清理日志、不停用账号、不隔离或重启生产主机，不进行反向攻击。
```

组织的隔离、封禁、凭据轮换和恢复工作仍应由负责团队按事件响应流程决定。

## 持续攻防、蓝队检测验证与整改复测

### 准备材料

准备明确的演练授权与 ROE：靶场或获准目标、时间窗口、允许的身份和方法、禁止操作、请求限速、停止条件及负责人。同时准备蓝队可提供的日志和检测结果、已确认问题与复现材料。

先约定哪些动作只做计划或本地演示，哪些可以在真实授权目标上验证。持久化、隐蔽、凭据窃取、自动横向移动、数据外传和破坏性动作不属于本工作流。

### Agent 如何组织工作

1. 将 ROE、业务目标和验收信号整理成计划，建立“测试动作—预期证据—蓝队观察—后续复测”的待办矩阵。
2. 从网络画像、应用接口、浏览器与代理证据中提出具体验证候选，按影响排序。版本或 CVE 匹配应作为候选，不能直接当成已经利用成功。
3. 对一个疑点提出最小、非破坏验证方法，在获得相应确认后执行；证据充分时停止增加探测。不同疑点分别验收，不把一个子项通过写成整个类别都已完成。
4. 将测试时间、请求标识与动作摘要提供给蓝队，对照其实际日志和检测结果。区分“检测到预期信号”“未检测到”和“日志或采集链路不足以判断”。外部告警平台需要已有导出或已配置集成，不能假定已自动接通。
5. 使用影响建模工具解释潜在影响与前提，或在确认后生成仅供本地实验的演示材料。影响规划工具不等于执行后渗透，本地演示也不能证明真实目标已被利用。
6. 由责任团队实施整改或规则变更，再按原条件复测。记录目标版本、身份和环境差异，更新问题与检测状态。

### 执行节奏

有限演练可在约定窗口中分阶段进行，只有真实的观察间隔才需要等待。需要跨多轮推进时，保存检查点并用 `session` 继续现有对话；长期任务可使用 `max_runs=0` 避免按固定次数结束，每段仍受时间、资源与授权边界约束。

持续验证可以安排在发布、规则变更或报告产生之后触发，也可以按固定窗口周期执行。每次只推进批准的下一步，等待人工决定时延期；任务完成、授权到期或出现停止条件时停止。运行次数与调度行为详见[自动化](Automation.md)。

### 证据与交付

交付应保留验证计划、实际执行动作、原始信号引用、蓝队观察、影响假设、未执行动作与整改复测结果。问题状态至少区分仍成立、原验证不再成立、环境变化无法比较和证据不足。工单关闭和风险接受由团队审批。

可复制任务：

```text
请在我提供的演练 ROE 内，组织一次受控验证与蓝队检测复核。
先读取目标清单、已有发现和检测说明，建立逐项待办、验收信号与停止条件。
一次只选择一个疑点，给出最小非破坏验证方案和预期日志标识，等待相应确认后执行。
把实际动作与蓝队提供的日志关联，区分检测有效、未检测与采集不足，并保留证据引用。
影响评估先做建模；本地演示不得连接真实目标，不得把演示结果当作实网利用证明。
责任团队整改后，用原条件复测，记录环境差异与下一步负责人。
不持久化、不窃取凭据、不自动横向移动、不外传数据，不执行破坏性载荷。
```

## 跨轮次保持进展

一次性检查、长期调查和周期巡检可以使用同一套证据组织方式，但运行方式应与目标相符。

| 工作方式 | 适合的任务 | 每次需要保存 |
| --- | --- | --- |
| 当前会话的一次性执行 | 上线审查、首次基线、有限事件调查 | 已完成步骤、证据、缺口与交付 |
| `session` 继续现有对话 | 未完成分析、长任务分段推进 | Todo、checkpoint、下一步与停止条件 |
| `dedicated_session` 任务专属对话 | 持续调查、重点资产跟踪 | 跨次假设、证据索引、状态变化 |
| `new_session` 独立运行 | 周期资产巡检、代理新流量复核 | 基线版本、检查范围、变化与结果摘要 |

较长手册放在知识库或 Skill，定时提示词只引用手册、冻结的资产范围和本次工作量。跨次任务上下文不要携带密码、私钥或 API Key。Webhook 可接收已对接的构建、告警或业务事件；文件监听只观察指定路径，避免分析输出再次触发相同任务。

每轮应说明“检查了什么、变化是什么、依据在哪里、还有什么没完成”。首次启用持续任务时，先观察有限几次运行与通知，再决定是否延长。自动巡检可以只在变化、失败或需要人工处理时通知，缺少有效进展时应复核计划，而不是单纯提高频率。

## 复测与知识积累

保留已确认问题的原始条件、复现依据和整改后条件，标明目标版本、身份和环境变化。将可复用的方法与已验证结论保存为知识条目；仍待验证的推断应保留状态，不应作为确定规则传播。

团队可让小队按应用、流量、主机与样本分工，群聊共享调查发现，私聊处理具体成员任务。小队属于运行时任务协作；企业人员身份、集中审计、生产处置与材料留存要求仍需结合现有系统落实。
