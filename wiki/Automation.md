# 定时任务、持续续跑与主动巡检

[Wiki 首页](Home.md) · [Agent 对话](Agent-and-Sessions.md) · [CLI 参考](CLI-Reference.md)

把需要长期完成的目标交给 Agent，让它建立计划、执行巡检并接续未完成工作。ArgusAI 按时间或事件唤醒 Agent，读取待办与证据后继续推进；定时任务页面用于检查计划、运行历史与通知。

可以直接从悬浮球或完整对话发出任务：

```text
请为已确认的测试服务建立每日巡检计划，每天 9 点执行。
按知识库中的资产范围与检查步骤工作，对照基线保存变化和证据。
只在有重要变化、执行失败或需要我处理时通知，并给出首次运行的核对方法。
```

下面说明如何选择持续方式、触发器与会话，以及怎样核对 Agent 创建的计划。

## 先选择持续方式

| 目标 | 优先方式 | 操作要点 |
| --- | --- | --- |
| 一个明确目标需要连续分析数十小时 | 单轮长时间 Agent 执行 | 核对“单次 Agent 最长运行时间”，维护待办与检查点；CLI 另行设置等待超时 |
| 一项扫描或工具执行很慢，但还要继续其他分析 | 支持后台模式的工具任务 | 保存 `job_ref`，在需要时查状态和结果，不把收据当作最终输出 |
| 每天巡检、事件触发，或在后续多轮继续工作 | 本页的 Cron 持久任务 | 选择触发方式、执行目的地、跨次状态与通知策略 |

三种方式可以组合：某次计划启动一轮分析，分析中把耗时扫描放到后台，后续再次触发时继续读取证据。应分别查看调度记录、Agent 对话与后台工具状态。单轮数十小时是原生循环与时长配置支持的工作方式，不是已经做过相同时长稳定性测试的结论。配置细节见[Agent 单轮长时间执行](Agent-and-Sessions.md#单轮长时间执行与三种持续方式)。

## 先确定任务的执行约定

创建计划前，应明确目标、允许的工具、每次执行的工作量、跨次状态存放位置和通知条件。把较长操作规范存为知识条目，在计划提示词中引用，便于后续维护。

需要模型、外部工具或网络的任务，依赖相应服务可用。调度器必须在线；保存计划本身不会让已关机的电脑继续运行。

## 四种触发方式

在侧栏 **定时任务** 中选择 **新建计划**，设置名称和任务提示词，再选择触发方式。

| 触发类型 | 配置内容 | 适用场景 |
| --- | --- | --- |
| 固定间隔 `interval` | 每次执行之间的间隔秒数 | 周期巡检、后台扫描状态跟踪、定期复查新发现 |
| Cron `cron` | 五字段 Cron 表达式 | 每日、每周或固定维护窗口的检查 |
| 签名 Webhook `webhook` | 触发地址、签名密钥、可选防抖 | 接收外部构建、告警或业务事件，开展后续分析 |
| 文件变化 `file_change` | 文件或目录、匹配规则、递归、轮询和防抖 | 新日志、扫描报告、样本或构建产物出现后分析 |

Cron 日历规则按运行主机的本地时间解释。迁到另一台主机或修改系统时区后，核对“下次执行”时间。固定间隔允许较短周期，但真实巡检通常应使用分钟级或更长间隔，并限制单次工作量。

文件监听按修改时间和文件大小轮询，保存时先建立基线，不会因为目录已经有文件就立即分析全部内容。它适合发现变化线索，不应当作逐字节文件完整性校验。

## 三种运行方式

触发方式和执行对话可分别选择。

| 界面选项 | 字段值 | 上下文如何保留 | 使用建议 |
| --- | --- | --- | --- |
| 每次新建会话 | `new_session` | 每次有独立运行对话；通过任务上下文、知识库、证据和运行记录传递状态 | 独立巡检、批量材料检查，避免占用人工对话 |
| 任务专属会话 | `dedicated_session` | 首次触发建立该任务私有的会话，以后复用 | 长期跟踪一个资产、项目或调查方向 |
| 固定会话 | `session` | 继续指定会话，保留原有历史、待办和检查点 | 当前 Agent 任务续跑、对现有分析安排复查 |

“每次新建会话”不会复制创建它的完整历史。把必要事实写入任务上下文或知识条目，明确证据引用，不要把密码和 API Key 写进提示词或上下文。运行历史中的“打开会话”指向该次实际执行的对话。

## 创建一项可验证的计划

1. 在 **定时任务 → 新建计划** 填写名称和提示词。
2. 选择触发方式，并填写间隔、Cron、Webhook 或监听路径。
3. 选择每次新建、任务专属或固定会话；固定会话需要明确目标对话。
4. 设置最大执行次数。`0` 表示不按次数限制；试用任务可先设置有限次数，核对行为后再调整。
5. 配置 **成功时通知**、**失败时通知**、**仅变化时通知** 与 **回报创建会话**。
6. 核对无人值守授权，保存后检查启用状态与下次执行时间。
7. 首次运行后打开 **执行记录**，检查结果、状态和运行会话，确认输出与通知符合预期。

运行中的状态可能是完成、失败、等待会话空闲、等待用户决定、等待工具确认或授权阻止。计划列表存在不代表它正在执行；判断应以实际运行记录为准。

## 长任务持续续跑

持续续跑使用固定会话，把“保存进度 → 再次唤醒 → 继续下一项”串起来。它是多次执行组成的持久任务，每一段仍受运行时间、上下文、资源和授权约束。

可以在当前对话要求：

```text
为当前分析建立持续续跑计划，每隔 10 分钟检查一次，固定到本对话，执行次数不设上限。
每次读取最近 Todo 和 checkpoint，只继续下一项未完成工作，不重复已完成步骤。
大输出保存为产物，只在对话中保留引用与结论。
全部完成后停用这项续跑计划并总结结果。
如果缺失必要信息、等待人工决定或没有有效授权，保持阻塞并通知我，不得猜测或绕过。
```

对应要点是 `destination=session`、当前会话 ID 与 `max_runs=0`。后者表示无固定执行次数上限，不是无条件、永不停止的单轮模型调用。

用户正在该会话交互、会话忙或等待必要人工处理时，调度会延期，不应启动另一个竞争执行。不要为了续跑设置秒级固定会话计划；高频独立检测更适合每次新建会话。

## 自动巡检与主动发现

### 应用上线前防护验证

一次复杂上线审查若需要持续梳理接口、追踪代码和完成多项验证，可在单轮中连续推进，保持待办、阶段报告与证据。耗时扫描交给支持后台模式的工具。发布后复查或每日基线检查则交给 Cron，避免占用同一个交互回合长期等待。

```text
围绕本次预发布变更持续完成应用安全检查。
以现有接口、JS、HAR 和测试账号为输入，按授权范围整理攻击面并验证新增疑点。
对认证、访问控制、输入处理和安全配置分别记录证据及覆盖情况。
每阶段保存 Todo 与 checkpoint；耗时扫描可使用后台任务，保留 job_ref 并最终读取结果。
交付上线前问题、复现条件、修复建议与发布后复查计划。
不要修改生产配置，不把没有证据的推测写成已确认漏洞。
```

这里的“防护”工作包括风险发现、验证、整改建议和复查。应用阻断、规则上线或自动修复如果要执行，应属于明确任务和权限范围，不能由“发现风险”自动推导出生产变更授权。

### 长期内网巡检与事件溯源

内网日常工作适合用 Cron 周期检查已授权资产的暴露面、服务状态与新增被动线索。每次独立巡检可用 `new_session`；长期追踪同一事件、资产组或问题时，用 `dedicated_session` 保留调查上下文；人工正在推进的调查可用 `session` 在合适时间接续。

```text
为授权的内网测试资产建立长期巡检，按已保存基线和检查手册执行。
定期整理服务变化、新增接口、异常流量与现有告警线索，记录时间和证据来源。
把需要进一步调查的问题汇入该任务专属会话，形成时间线、假设与待验证项。
只有重要变化、执行失败或需要人工处置时通知；无变化时安静结束。
需要跨机器操作时，只使用已授权的连接与命令，不将本机结果冒充远端资产状态。
```

日志、流量和样本可共同支持事件溯源，但结论需要对应的时间线和材料。工作台不会凭空获得组织全部资产或日志，也不会把一个线索自动变成已经确认的攻击路径。

### 持续攻防验证

在约定靶场或测试环境中，可把受控验证、检测观察和修复复测组织成周期任务。单轮用于完成一次多步骤验证，后台任务承载耗时工具，Cron 用于在新构建或固定窗口重新检查。

在提示词中记录允许验证的方法、影响上限、检测侧观察方式和停止条件。每次产物应关联到目标版本、验证证据和检测结果；攻击验证与蓝队观察分别记录，避免把工具运行成功等同于检测有效或问题已修复。

### 每日资产变化检查

先保存已授权目标、基线、检查步骤和发现判定方法，再配置日历计划：

```text
每天在约定检查窗口复核知识库中列出的测试服务。
仅使用已授权的基础探针，检查可达性、TLS、请求头与接口变化。
对照上次记录整理新增资产或配置变化，并保存证据。
无变化时安静结束；出现新增风险、执行失败或需要人工处理时通知我。
不扩大目标，不改写流量，不执行修复或服务重启。
```

输出应包括本次范围、对比依据、变化项和证据引用。新线索需要进一步验证时，建立待办，不能只凭“与上次不同”认定为漏洞。

### 代理新流量复核

使用固定间隔检查代理新增流量与被动发现，按接口、状态码或业务路径筛选。把值得调查的请求关联到 Case 或 ReverseJob，定期汇总“新增线索、已核实、仍待确认”三类结果。

### 新报告或样本出现后分析

监听一个指定目录，设置匹配规则和防抖。提示词应要求只处理本次变化涉及的材料，记录输入路径或产物引用，并避免循环改写被监听文件导致重复触发。

### 外部事件驱动分析

Webhook 适合测试构建完成、外部告警或流程事件。事件发送端需要对接 ArgusAI 的签名格式：

```text
X-ArgusAI-Timestamp: <Unix 时间戳>
X-ArgusAI-Event-Id: <本事件的唯一标识>
X-ArgusAI-Signature: sha256=<HMAC-SHA256 十六进制结果>

签名内容 = timestamp + "." + 原始请求体字节
```

签名密钥在创建或轮换时显示，之后隐藏。轮换会使旧密钥失效，需要同步更新调用方。发送端应对同一事件重试复用事件 ID。默认回环监听只适合本机调用；对外暴露需要结合网络边界、认证 HTTPS 反向代理和可达地址配置。

## 无人值守授权和通知

计划创建或启用后，普通工具、待办计划和可自动处理的决策可以继续执行。高风险工具还需要该计划的独立授权；GUI 中有 **自动审批所有操作（含高风险工具）** 及确认流程。授权后该计划后续触发不会逐次再询问；缺失授权时应失败并报告。

会话输入栏的自动审批只影响当前对话，不能替代定时任务的高风险授权。创建会话的显式工具与 MCP 授权也会影响新执行会话；不要用调度获得比原授权更大的权限。

“仅变化时通知”用于减少重复回报。业务层面什么算变化，应在提示词中写清楚，并保存可比较的基线；更换提示词或基线时，也应查看一次实际运行结果。

## 让调度器常驻

桌面运行时可以托管计划；无需桌面窗口时，在终端运行：

```sh
uv run argusai serve run --cron-only
```

同时托管通信渠道与计划：

```sh
uv run argusai serve run
```

这是前台服务，终端关闭或进程退出后停止。需要系统级常驻可查看：

```sh
uv run argusai serve install --dry-run
uv run argusai serve status
```

同一数据根目录的宿主应按程序的单实例管理要求运行，避免 GUI 与另一个服务竞争。源码环境注册系统服务后，不要随意移动仓库或重建对应解释器。完整命令见[CLI 参考](CLI-Reference.md)。

## 检查和停止

在 GUI 关闭某项计划的启用开关可以暂停后续触发。删除计划会永久删除该计划及其运行历史，保留调查依据时优先暂停并导出所需材料。

CLI 可以先查看再操作：

```sh
uv run argusai cron list
uv run argusai cron --help
```

任务没有触发时，依次查看：宿主是否在线、计划是否启用、下次执行时间、目标会话是否忙、事件是否已排队、监听路径或签名是否正确、高风险授权是否缺失。不要仅通过提高频率来排查。
